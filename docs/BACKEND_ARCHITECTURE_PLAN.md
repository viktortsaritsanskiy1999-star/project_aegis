# Архитектурный план приватного локального Backend Project Aegis

> **Документ:** `docs/BACKEND_ARCHITECTURE_PLAN.md`  
> **Версия:** 1.0.0  
> **Статус:** Черновик архитектуры (Draft Architecture Plan)  
> **Окружение:** Локальный компьютер под управлением Windows (Local Windows Workstation)  
> **Целевая система:** Project Aegis (Flutter Client + Private Local Backend + Google Gemini API)  

---

## 1. Введение и цели архитектуры

Project Aegis эволюционирует от автономного мобильного приложения к распределённой гибридной архитектуре с выделенным **приватным сервером на локальном компьютере Windows**. 

### Ключевые цели перехода:
1. **Защита клинических слоёв ИИ:** Внутренние рассуждения моделей, аудит ошибок, глубокие дифференциальные гипотезы и биомеханический анализ не должны храниться или обрабатываться на пользовательском мобильном устройстве.
2. **Юридическая и психологическая безопасность пользователя:** Пациент в интерфейсе приложения видит только велнес-рекомендации, пользовательские резюме и диалог с Афиной, исключая панику от сырых клинических терминов и гипотез.
3. **Безопасность учетных данных:** API-ключи Google Gemini полностью изолируются в защищенном контуре Windows-сервера. Клиентское мобильное приложение никогда не имеет прямого доступа к API-ключам.
4. **Масштабируемость аналитики:** Тяжелые вычисления каскадов моделей (8 системных агентов Flash-Lite, Замглавврача Flash 3.6, Главврач Pro 3.1, будущий Workout Intelligence) выполняются сервером, не расходуя аккумулятор смартфона.
5. **Медицинская преемственность:** Хранение полных медицинских циклов (`cycle_id`), включающих множественные недельные спринты Афины, и серверная сборка структурированных информационных отчетов наблюдений (PDF/DOCX) для обсуждения с очным врачом на базе `hospital_referral_document.dart`.

## 3. Разделение данных и модель изоляции (Data Partitioning)

### 3.1. Клиентский контур (Client-Facing Tier)
В мобильном хранилище (`VaultService` на устройстве) остаются **исключительно пользовательские артефакты**:
* **Полки органов `system_general_shelf`:** лаконичные выжимки для интерактивного Атласа человека на понятном языке.
* **Главный маршрут `pro_general_shelf`:** мета-план оздоровления без дифференциальных диагнозов и пугающих патофизиологических связок.
* **Диалог с Афиной (`curator_chat_history`):** история общения с поддерживающим ментором.
* **Пользовательский отчет тренировок `user_workout_report`:** понятные метрики выносливости, темпа, пульсовых зон и советы по восстановлению.
* **Адаптивные пороги пульса (`min_pessimum_bpm`, `max_pessimum_bpm`):** численные границы для работы локального монитора `VitalsMonitorService` без раскрытия клинического обоснования врача.

### 3.2. Приватный серверный контур (Private Clinical Tier)
На локальном Windows-сервере персистентно хранятся **закрытые клинические уровни**:
* **Полки `system_training_shelf` 8 систем:** сырые рассуждения, обнаруженные дефициты маркеров, пограничные риски, списки исключенных патологий.
* **Полка аудита `flash_training_shelf`:** межорганный аудит Замглавврача (Flash), критика ошибок первичных агентов, конфликтные гипотезы.
* **Полка Главврача `pro_training_shelf`:** итоговый клинический разбор, скрытые триггеры декомпенсации, медицинский маршрут.
* **Закрытый анализ тренировок `internal_analysis`:** клинический и кардиореспираторный разбор нагрузки (оценка аритмических рисков, динамика ST-сегмента при наличии ЭКГ, восстановление ЧСС по зонам).
* **Скрытый клинический дневник Афины (`athena_clinical_logs`):** структурированные блоки `[CLINICAL_REPORT]`, формируемые Афиной в каждом ответе для консилиума.
* **Полный аудит промптов и сырых ответов моделей:** сырые JSON-ответы, токены и технические логи.

## 4. Структура SmartWatch на клиенте и сервере

В соответствии с уже реализованной в коммите `f5f2dc8` архитектурой `health_systems → cvs → markers → smart_watch`, хранение делится на два взаимосвязанных уровня:

### 4.1. Клиентское хранилище SmartWatch (Mobile Vault)
* `workout_sessions` — массив сессий с метаданными:
  * `session_id` — уникальный строковый ключ тренировки (`ws_${timestamp}`).
  * `anomaly_detected_at` — момент фиксации первого скачка.
  * `activity_confirmed_at` — момент нажатия пользователем «Да».
  * `workout_completed_at` — момент нажатия «ТРЕНИРОВКА ЗАВЕРШЕНА».
  * `physiological_end_time` — момент физиологического восстановления ЧСС (база $\times 1.15$).
  * `status` (`active`, `recovering`, `completed`).
  * `is_data_collection_finished` — статус закрытия окна сбора.
  * `missed_samples` — пропуски и интервальные пробелы.
* `heart_rate_samples` — точки замеров с источниками (`watch_sensor`, `manual_input`, `test_chip`, `simulated`, `unknown`).
* `workout_context` — базовый контекст тренировки.
* `workout_analysis_reports` — массив отчетов с версионированием, содержащий **только**:
  * `report_id`, `version`, `created_at`.
  * `user_workout_report` (заполнен).
  * `athena_handoff` (заполнен).
  * `internal_analysis: null` (клиент видит `null`, поле физически не передается с сервера на клиент).

### 4.2. Серверное хранилище SmartWatch (Server Database)
Сервер дублирует сессию под тем же `session_id`, но дополняет её:
* Полным объектом **`internal_analysis`**:
  * Расчет зон ПАНО/АНО.
  * Оценка вегетативного тонуса и симпатического преобладания.
  * Кардиоваскулярная цена нагрузки.
  * Маркеры риска скрытой ишемии или электрической нестабильности миокарда.
* Несжатой исходной телеметрией часов (включая будущие сырые акселерометрические и PPG-данные Samsung SDK).

## 5. Безопасность и управление Gemini API-ключом

### 5.1. Хранение API-ключа на Windows-компьютере
1. **Исключение утечки в кодовую базу:** 
   * API-ключи никогда не коммитятся в Git (строгое правило `.gitignore`).
   * Ключ читается из защищенного файла конфигурации `.env` на сервере:
     ```env
     AEGIS_SERVER_PORT=8080
     AEGIS_SERVER_HOST=127.0.0.1
     GEMINI_API_KEY=your_gemini_api_key_here
     AEGIS_STORAGE_PATH=C:/Users/.../AppData/Local/AegisServer/data
     AEGIS_CLIENT_AUTH_SECRET=aegis_secure_local_token_...
     ```
2. **Аппаратное шифрование (Production Windows Profile):**
   * Для промышленного развертывания на Windows используется **Windows Data Protection API (DPAPI)** через библиотеку `crypt32` / Windows Credential Vault. Ключ расшифровывается в оперативной памяти сервера только в момент обращения к процессу.

### 5.2. Авторизация мобильного клиента
* При первом сопряжении приложения с локальным сервером (через QR-код или ручной ввод локального IP-адреса) генерируется симметричный криптографический токен устройства (`device_auth_token`).
* Все клиентские запросы сопровождаются заголовком:
  ```http
  Authorization: Bearer <device_auth_token>
  X-Aegis-Cycle-Id: <current_cycle_id>
  ```
* Сервер отклоняет любые внешние неавторизованные запросы. Доступ по умолчанию ограничен локальной подсетью (`127.0.0.1` или доверенный диапазон домашнего Wi-Fi).

## 6. Сквозная интеграция с HealthDataProvider и Samsung SDK

В коммитах `2a4c5d7` и `588bcd9` был создан универсальный `HealthDataProvider` со строгим контролем источников и разделением потоков. Серверная архитектура полностью опирается на этот контракт:

### 6.1. Типизация источников
Сервер валидирует входящие пакеты биометрии по перечислению `HealthDataSource`:
* `watch_sensor` — реальные замеры пульса и сенсоров часов.
* `manual_input` — данные, введенные пользователем вручную.
* `test_chip` — проверочные значения отладки.
* `simulated` — виртуальное тестовое время.
* `unknown` — безопасный статус для нестандартных или неопознанных пакетов (никогда не повышается до `watch_sensor`).

### 6.2. Протокол передачи Live и Исторических данных на Сервер
* **Live-телеметрия (`/api/v1/vitals/stream`):**
  * Потоковая передача по WebSocket или легковесным HTTP POST.
  * Сервер регистрирует точки и, при необходимости, передает их в фоновый процесс серверного мониторинга.
* **Исторический пакетный импорт (`/api/v1/vitals/batch`):**
  * Пакеты передаются с флагом `asHistorical: true`.
  * Сервер сохраняет их в историческую базу медицинского цикла с сохранением оригинальных меток `measured_at` и времени импорта `ingested_at`.
  * Исторические пакеты **никогда не активируют live-тревоги тахикардии** и не запускают ложных модалок на клиенте.
* **Готовность к Samsung Privileged Health SDK:**
  * Samsung SDK передает пакеты с задержкой (batch synchronization). Серверный контроллер будет принимать их напрямую в коллекцию `heart_rate_samples` без искажения истории тренировок.

## 7. Концепция медицинских циклов (`cycle_id`) и недельных спринтов

Для обеспечения непрерывности и целостности данных Project Aegis вводит двухуровневую иерархию времени: **Медицинский Цикл (`Medical Cycle`)** и **Недельные Спринты (`Weekly Sprints`)**.

### 7.1. Что такое `cycle_id` и как он соотносится со спринтами
* **`cycle_id` (Полный медицинский цикл):** Это сквозной идентификатор глобального периода медицинского наблюдения пациента в системе Aegis (макроцикл, охватывающий несколько недель или месяцев от первичного чекапа до контрольного лабораторного обследования или пересмотра стратегии).  
  Формат: `cycle_YYYYMMDD_UUID` (например, `cycle_20261016_a1b2c3d4`).
* **Недельный спринт (`sprint_number` / `sprint_id`):** Внутри одного медицинского цикла последовательно проходит **множество 7-дневных спринтов куратора Афины**. Каждый спринт имеет свой номер `sprint_number` (1, 2, 3...) или идентификатор `sprint_${cycle_id}_w1`, `sprint_${cycle_id}_w2`.

### 7.2. Жизненный цикл и правила завершения
1. **Инициация медицинского цикла (`cycle_id`):**
   * Создается при первичном подключении к системе или при открытии нового глобального периода наблюдения.
   * Связывает воедино базовый анамнез, первичные лабораторные тесты и целевые установки.
2. **Прохождение спринтов внутри цикла:**
   * Внутри активного `cycle_id` дни спринта отсчитываются от 1 до 7 (`athena_sprint_day`).
   * К активному спринту и циклу привязываются: ежедневные замеры, тренировочные сессии `workout_sessions`, дневники Афины (`athena_clinical_logs`).
3. **Завершение 7-го дня спринта (Окончание недели):**
   * **Седьмой день НЕ закрывает медицинский цикл `cycle_id`!**
   * Завершение 7-го дня означает окончание очередного недельного спринта: Замглавврача (Flash) и Главврач (Pro) через `WeeklySprintCascadeService` подводят промежуточные итоги недели, обновляют акценты для Афины, инкрементируют номер спринта (`sprint_number++`) и сбрасывают счетчик дней спринта на 1 (`athena_sprint_day = 1`).
   * Медицинский цикл `cycle_id` продолжается дальше в рамках обновленной стратегии.
4. **Финализация медицинского цикла:**
   * `cycle_id` закрывается отдельно (вручную пользователем/врачом или при назначении повторного полного чекапа со сдачей контрольных панелей анализов).
   * При закрытии цикла формируется неизменяемый архив всего периода (`CycleSnapshot`), фиксирующий динамику за все прошедшие недели.

## 8. Серверный генератор информационных отчетов для обсуждения с врачом (Physician Observation Summary Engine)

В кодовой базе Project Aegis заложен механизм формирования клинической сводки в файле `lib/services/hospital_referral_document.dart` (`DecompensationReportCascadeService`).

### 8.1. Статус документа и правовой дисклеймер
* **Информационный статус:** Формируемый PDF/DOCX документ является **структурированным информационным отчётом наблюдений для обсуждения с очным врачом (Clinical Observation Summary / Health Monitoring Report for Physician Discussion)**.
* **Не является диагнозом:** Документ **НЕ является официальным медицинским направлением, диагнозом или врачебным заключением лицензированного врача**. Его задача — предоставить очному доктору объективные хронологические данные (динамику ЧСС, скачки, лабы, декомпенсационные маркеры), которые пациент не сможет точно пересказать по памяти.
* **Обязательный дисклеймер на бланке:**
  > *«ВНИМАНИЕ: Настоящий документ сформирован аналитической системой Project Aegis на основе цифрового мониторинга и ИИ-анализа витальных показателей. Документ носит исключительно информационно-ознакомительный характер для предоставления лечащему врачу, не подменяет очную медицинскую консультацию и не является официальным медицинским диагнозом или направлением на госпитализацию.»*

### 8.2. Двухстадийный каскад генерации отчета наблюдений
```
┌────────────────────────────────────────────────────────────────────────┐
│               PHYSICIAN OBSERVATION SUMMARY CASCADE (SERVER)           │
```

### 8.3. Форматы экспорта
* **PDF (Portable Document Format):** Структурированный отчет для печати или отправки доктору. Содержит график динамики пульса за период наблюдения, сводную таблицу отклонений лабораторных маркеров, перечень жалоб из дневника Афины и обязательный дисклеймер.
* **DOCX (Microsoft Word):** Редактируемый файл для удобного копирования данных анамнеза врачом в электронную медицинскую карту.

## 9. Спецификация REST API приватного сервера

Сервер реализует версионированный REST API (`/api/v1`):

### 9.1. Управление медицинскими циклами
* `POST /api/v1/cycle/start` — запуск нового медицинского цикла.
* `GET /api/v1/cycle/current` — получение метаданных активного цикла.
* `POST /api/v1/cycle/close` — завершение текущего цикла и запуск итогового недельного консилиума.

### 9.2. Каскадный консилиум органов и систем
* `POST /api/v1/cascade/run-system` — запуск анализа конкретной системы организма (принимает анамнез + лабы, сохраняет приватную полку на сервере, возвращает клиенту только `general_shelf`).
* `POST /api/v1/cascade/run-master` — запуск этапа Замглавврача (Flash) и Главврача (Pro). Возвращает клиенту `pro_general_shelf` и числовые `vitals_thresholds`.

### 9.3. Биометрия и телеметрия HealthDataProvider
* `POST /api/v1/vitals/measurement` — передача единичного живого замера с явным источником (`HealthDataSource`).
* `POST /api/v1/vitals/batch` — пакетный импорт исторических данных с флагом `asHistorical: true`.
* `GET /api/v1/vitals/history?session_id=...` — получение выборки пульсовых точек.

### 9.4. Тренировки и Workout Intelligence
* `POST /api/v1/workout/session/create` — регистрация начала тренировочной сессии (`session_id`, `anomaly_detected_at`, `activity_confirmed_at`).
* `POST /api/v1/workout/session/complete` — фиксация окончания тренировки (`workout_completed_at`, `physiological_end_time`).
* `POST /api/v1/workout/analyze` — запуск серверного модуля **Workout Intelligence**:
  * Сервер выполняет анализ сессии через Gemini Pro.
  * Сохраняет `internal_analysis` в защищенную БД сервера.
  * Возвращает клиенту объект с `user_workout_report` и `athena_handoff`.

### 9.5. Документооборот и информационные отчеты для врача
* `POST /api/v1/reports/observation-summary/generate` — запуск генерации информационного отчета наблюдений для очного врача на базе `DecompensationReportCascadeService`.
* `GET /api/v1/reports/observation-summary/download?format=pdf|docx` — скачивание скомпилированного информационного отчета.

## 10. Рекомендуемый технологический стек сервера

Для реализации на локальной машине Windows рекомендуется легковесный, производительный и строго типизированный стек:

1. **Ядро бэкенда:** **Python 3.11+ / FastAPI**
   * Нативная асинхронность (`asyncio`) для параллельного опроса 8 системных агентов через официальный SDK `google-genai`.
   * Высокая скорость валидации данных через `Pydantic v2`.
   * Автоматическая генерация документации OpenAPI (Swagger UI) на `http://127.0.0.1:8080/docs`.
2. **База данных:** **SQLite (с поддержкой WAL-режима) / PostgreSQL**
   * На этапе локального использования SQLite обеспечивает нулевой оверхед по администрированию, храня всю медицинскую базу в одном файле `aegis_private_vault.db`.
   * Поддержка шифрования файла базы через SQLCipher при необходимости максимальной защиты.
3. **Генерация клинических документов:**
   * **PDF:** `WeasyPrint` (HTML/CSS $\rightarrow$ PDF типографского качества) или `ReportLab`.
   * **DOCX:** `python-docx` с шаблонизацией медицинских бланков.
4. **Конфигурация и секреты:** `pydantic-settings` + `.env` с хранением ключей в закрытом каталоге пользователя Windows (`%LOCALAPPDATA%/AegisHealth/Server`).
